# Business OS portfolio: правила для агентов (Codex, Claude Code)

Это публичная демонстрационная реконструкция с синтетическими данными DemoBrand. Это не рабочая Business OS и не разрешение обращаться к её сервисам.

## Задача и роли

Сначала назвать результат для владельца, входные данные, критерии приёмки, допустимые изменения и стоп-условие. Неизвестное не подменять нулём.

Владелец определяет бизнес-правила и принимает решения. Агент (Codex или Claude Code; для Claude Code см. также `CLAUDE.md`) реализует ограниченную задачу, добавляет тесты и показывает результат. Проверяющий оценивает конкретный diff и доказательства.

## Карта

- `sql/`: неизменяемые наблюдения, параметры, SQL-представления.
- `scripts/render_report.js`: единственный исходник рендера.
- `scripts/n8n_report_glue.js`: адаптер для Code-узла.
- `workflows/`: выключенные обезличенные экспорты. Правка JSON не является deployment.
- `llm/`: вопросы владельца по фактам: маскирование (`llm/config/masking.json`), промпт и гейт ответа (`llm/answer.js`), детерминированный грейдер, eval (`llm/eval/`).
- `scripts/promo_decision.js`: контракт кнопок решения по акциям (PRD 002).
- `site/`: статическая демо-страница из выходов демо.
- `tests/`: регрессии отчёта, инструментов, настоящей PostgreSQL, Q&A и кнопок.
- `docs/prd/`: PRD; `docs/tasks/`: постановки с критериями; `docs/verification-v051.md`: реальные результаты.

## Границы

- Только локальная работа с синтетикой. Не подключаться к Neon, n8n, Ozon или Telegram.
- Не читать приватные журналы, дампы, `.env` и внешние каталоги с секретами. Не копировать реальные SKU, chat id или credential binding.
- Не отправлять сообщения, не менять цены, рекламу, заказы или остатки. Deployment требует отдельной точной авторизации.
- Не запускать reset на произвольном `DATABASE_URL`. Демо принимает только локальную БД `bos_portfolio_demo` без дополнительных параметров соединения.
- LLM не считает бизнес-цифры: их считает SQL. Ответ модели показывается только после грейдера (`llm/grader.js`). Не ослаблять грейдер ради прохождения eval; у каждого файла ответов честный `source`: `GROK_BOT` (Grok Bot — настольный ассистент владельца, подключённый к Neon и n8n; не вызов API) или `HAND_WRITTEN_FIXTURE` (только тесты). API-клиента модели в системе нет и добавлять его без решения владельца нельзя. Записанные ответы после проверки не править.
- Модельная маржа и начисления показываются отдельно. Ставки, НДС, себестоимость и прогнозы подписаны как допущения.
- Не выдавать тест за production acceptance. Не придумывать commits, uptime или финансовые результаты.
- Не коммитить и не публиковать изменения без просьбы пользователя.

## Цикл

1. Прочитать модуль и постановку задачи.
2. Написать тест наблюдаемого поведения. Для новой логики увидеть ожидаемое падение.
3. Сделать минимальную правку, не менять соседние бизнес-правила без основания.
4. После правки рендера/адаптера выполнить `python scripts/inline_renderer_into_workflow.py`.
5. Выполнить `python scripts/check.py` (включает `node --test` и eval) и `npm test`; для SQL также `python scripts/check.py --sql` на загруженном демо. Демо не должно менять `examples/` (`git diff --exit-code examples/`).
6. Выполнить `python scripts/scan_secrets.py`. Нет Gitleaks = проверка не проведена, не PASS.
7. Показать diff, результаты и неизвестное. Публикация остаётся отдельным решением.

Стенд: `docker compose up --build --abort-on-container-exit --exit-code-from demo`. Он не запускает n8n, не отправляет Telegram и не наследует ключи рабочего окружения. Результаты: `demo-output/`.
