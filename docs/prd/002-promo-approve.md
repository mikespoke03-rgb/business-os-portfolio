# PRD 002: решение по акциям кнопками в Telegram

Статус: контракт кнопок реализован и покрыт тестами (задача 002); журнал решений и n8n-обработчик запланированы (задачи 003–004).

## Проблема

Утренний отчёт уже считает по каждой ближайшей акции рекомендации ENTER / DONT / OWNER_DECIDES и предупреждает об автодобавлении. Решение владелец принимает в кабинете маркетплейса, и нигде не остаётся записи: что рекомендовала система, что решил владелец, когда. Через месяц нельзя проверить, были ли рекомендации полезны, а автодобавление может пройти незамеченным.

## Цель

Владелец принимает решение по каждой SKU в акции одним нажатием в Telegram, а система записывает решение, ничего не меняя в маркетплейсе.

## Метрики

- Доля SKU из рекомендаций, по которым есть записанное решение до старта акции. Цель (гипотеза, ещё не согласована с владельцем): не меньше 90% через 4 недели после запуска. Основание: сейчас решения по парам SKU × акция не записываются отдельными строками (фиксируются пакетами в общем журнале), то есть база близка к 0%; в расчёте на 09.10 около четверти пар SKU × акция требовали решения владельца, остальные система относила к «не входить».
- Число случаев, когда товар попал в акцию автодобавлением без записанного решения. Цель: 0.
- Совпадение решения владельца с рекомендацией. Это не цель, а диагностика порогов `promo_min_margin_pct` и `promo_target_margin_pct`.

## Пользователь и сценарий

1. Утром бот присылает сообщение по ближайшей акции: список SKU с рекомендацией и маржой (или «маржа: нет данных»), под каждой SKU кнопки ✅ / ❌.
2. Владелец нажимает. Бот отвечает «записано: DEMO-001 — входить», сообщение остаётся.
3. Владелец сам включает или не включает товары в кабинете. Система не вызывает методы записи API.

## Критерии приёмки

- AC1. На каждую SKU две кнопки; `callback_data` не длиннее 64 байт (ограничение Telegram); текст говорит, что ничего не включается автоматически; отсутствующая маржа показана как «нет данных».
- AC2. Нажатие владельца превращается в решение {акция, SKU, APPROVE/REJECT, дата}.
- AC3. Отклоняются: нажатие не владельцем, кнопки прошлого дня, акция уже стартовала, подделанные или повреждённые данные.
- AC4. Каждое нажатие — событие в журнале. Ключ идемпотентности — id события доставки Telegram (`callback_query.id`): повторная доставка того же нажатия не создаёт дубль. Новое нажатие владельца — новая версия решения по паре акция × SKU (порядок — по возрастающему `update_id`), даже если оно повторяет более раннее решение: «да → нет → да» — три строки, действует последнее. История не перезаписывается; кнопки прошлого дня по-прежнему отклоняются (AC3). Поле `executed` всегда false.
- AC5. Журнал append-only (тот же триггер, что у `raw.*`); отчёт на следующий день показывает число решённых и нерешённых SKU по акции.
- AC6. Ни один узел workflow не вызывает методы маркетплейса, меняющие акции (проверка экспорта в `check.py`).

## Вне рамок

Автоматическое включение в акции, изменение цен, решения не владельцем, оценка эффекта акции на продажи.

## Риски

- Владелец может нажать, но не сделать действие в кабинете: журнал фиксирует намерение, а не факт. Сверка с `promo_action_product_obs` — отдельная задача после 004.
- Токен бота и chat id остаются в n8n credentials, не в коде.
