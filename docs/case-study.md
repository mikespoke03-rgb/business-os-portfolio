# Business OS: от вопросов владельца к проверяемому утреннему отчёту

## Задача и моя роль

Я владелец небольшого косметического бренда (Ozon FBO + розничная сеть). Продажи, реклама, остатки, документы сети и план денег жили в разных местах. Каждое утро нужно было понять: покрываем ли расходы, где заканчивается товар, входить ли в акцию, хватит ли денег на закупку до выплат, и какие из этих цифр свежие, а какие нет.

Я сформулировал вопросы и бизнес-правила, проверял финансовую логику, писал критерии приёмки и решал, что можно менять в работающей системе. Код (SQL, n8n, рендер отчёта, проверки) писали AI-агенты (Codex, Claude Code) по моим постановкам; каждую правку я принимал по результату тестов и сверке с данными.

Масштаб (на 10.10.2026): около 70 SKU на маркетплейсе плюс розничный канал; 7 типов источников данных (Seller API и Performance API маркетплейса, страница цен кабинета, сайт и документы розничной сети, курс ЦБ, вводы владельца со статусами «со слов» и «оценка»); около 70 активных workflow n8n по расписанию; журнал решений — больше 600 записей за две недели с 25.09. Рабочий проект в Neon создан в середине августа 2026; данные маркетплейса в базе — с конца июля (всё, что раньше, бралось из ручных выгрузок); единый утренний отчёт в Telegram — с начала октября. Учёт трудозатрат не вёлся.

## Решения, которые можно проверить

| Потребность владельца | Решение | Где проверить |
|---|---|---|
| Не путать сбой загрузки с нулём продаж | У каждой цифры дата данных; «нет данных» вместо 0 | `tests/renderer.test.js`, `tests/test_sql.py` |
| Не считать повторную загрузку новой выручкой | Неизменяемые снимки, берётся последний по бизнес-ключу | SQL-тест последнего наблюдения |
| Видеть и модельную маржу, и фактическую | Две отдельные цифры, никогда не складываются | SQL-модели, тесты рендера |
| Не получить отчёт дважды | Ключ «один раз в день» резервируется до отправки в Telegram | Тест выполняет SQL из экспорта workflow дважды |
| Видеть время в московском, где бы ни работала база | Экспорт фиксирует часовой пояс сессии, рендер переводит метки в Москву | Тест экспорта в UTC-сессии (v0.3) |
| Спрашивать словами, не рискуя выдуманными числами | LLM только формулирует по фактам SQL; ответ проходит детерминированный гейт | `docs/llm-eval.md`, `npm test` |
| Ничего не менять в маркетплейсе без меня | Сборщики только читают; решения по акциям — запись намерения, не действие | `scripts/check.py` (запрет методов записи), PRD 002 |

## Как устроен AI в системе

1. **Цифры считает SQL, а не модель.** Сборщики n8n кладут ответы API в неизменяемые снимки, представления считают маржу, безубыточность, рекламу, акции, отгрузки и кассу, проверки свежести и сверка двух API. Итог — один JSON `analytics.v_report_facts`. В ежедневном отчёте LLM нет: рендер детерминированный.
2. **AI-агент владельца — интерфейс к фактам.** AI-слой системы — Grok Bot, мой настольный AI-ассистент, подключённый к Neon и n8n. Он отвечает на вопросы и помогает разбирать отклонения. Он читает готовые факты и представления, а не пересчитывает цифры сам. Если факта нет, правильный ответ — «нет данных».
3. **Как такой интерфейс проверяется.** Модуль `llm/` показывает это на синтетике: прежде чем попасть в промпт Grok Bot, факты маскируются (названия товаров → коды SKU, себестоимость и контрагенты не уходят, касса округлена), ответ обязан ссылаться на ключи фактов, а грейдер сверяет каждое число, дату и время с этими фактами. Ответ, не прошедший проверку, не показывается. В eval 15 вопросов, включая «нет данных» и вопросы вне области; 9 намеренно плохих ответов должны отклоняться, и тесты это проверяют. Ответы для eval записаны через сам Grok Bot (без API-ключа): для каждого вопроса сохранён точный промпт модуля с замаскированными фактами, ответы записаны до проверки и не правились; результат 15/15. Оговорка: та же сессия раньше составила вопросы, так что это проверка формата и опоры на факты, а не слепой бенчмарк. Своего API-клиента модели в системе нет: AI-слой — только Grok Bot.
4. **Агенты разработки работают по правилам репозитория.** `AGENTS.md` (и `CLAUDE.md` для Claude Code): сначала критерии приёмки, затем падающий тест, минимальная правка, `check.py`, проверка секретов, показ diff. Публикация и деплой — отдельное решение владельца.

## Что изменилось для бизнеса

По оценке владельца, система экономит около 4 рабочих часов в день.

| Было | Стало |
|---|---|
| Данные маркетплейса за период до конца июля — ручные выгрузки с ноутбука | Ежедневные загрузки по расписанию (заказы, начисления, остатки, реклама, цены, акции) с проверкой «распарсено = записано» |
| Несколько утренних сводок, частично дублирующих друг друга; старая сводная таблица фактически не обновлялась с середины августа | Один отчёт в 09:00, у каждой цифры дата данных, устаревшее подписано как устаревшее |
| Рекомендации по отгрузкам в кластеры владелец просил получать ежедневно, их не было | Расчёт отгрузок по фактическим долям кластеров и команда «отгрузки» в Telegram (с 06.10; плановая рассылка пока в теневом режиме) |
| Вопрос «в каких акциях товар участвует и не упала ли цена ниже порога» был в списке первоочередных у владельца и не имел ответа | Ежедневный расчёт SKU × акция: маржа по цене акции, нужный рост продаж, рекомендация; решение остаётся за владельцем |

Что по-прежнему вручную: остаток на счёте (со слов владельца), документы розничной сети, PDF страницы цен кабинета, остаток собственного склада и любое изменение в работающей системе — только после фразы-одобрения владельца.

Деньги ниже — в долях дневной планки безубыточности (постоянные расходы и проценты на один день), абсолюты не раскрываются.

1. **Вывод из акций товаров с повышенной ценой (09.10).** Расчёт показал: из 62 SKU с повышенной ценой 42 продавались по цене акции, и у трети из них повышение полностью съедала скидка акции. Недополученная маржа — оценка около четверти дневной планки. Владелец решил вывести эти SKU; агент исполнил по одобрению, с копией «до», проверкой «после» и записью в журнал решений: 52 участия в акциях → 0, 112 из 112 строк автодобавления удалены, 0 отказов, цены не менялись. Итог по продажам ещё не измерен: база для сравнения сохранена, проверки назначены на 16.10 и 23.10.
2. **Повышение цен 04–07.10 (62 из 69 SKU).** Карточка «решение → эффект» разложила изменение маржи в день: итог положительный, около 35–40% дневной планки, но почти весь плюс дали отключение платных услуг продвижения, более дешёвый клик и меньший расход на оплату за заказ. Вклад самой цены пока около нуля или отрицательный. Система не дала приписать эффект повышению цены; отдельная проверка цены — 19.10.

## Истории инцидентов

**Инцидент 1. Лимит API и ложный «зелёный» запуск (07–08.10).**
- Что сломалось: пересчёт заказов за день падал на ответе 429 (лимит запросов в секунду). Настроенные повторы фактически не работали: n8n ограничивает паузу между повторами 5 секундами, и все 4 попытки укладывались примерно в 16 секунд. Окно перечитки за 7 дней продолжало работу после упавшего дня и завершалось зелёным.
- Как заметили: при разборе журнала запусков — пересчёт одного дня завершился ошибкой, а запуск окна, который его вызывал, остался зелёным.
- Что изменили: повторы с паузами 20/40/60/60 секунд внутри запуска; если 429 остаётся после 5 попыток — явная ошибка `D05_ANALYTICS_HTTP_429_AFTER_BACKOFF`; в окно перечитки добавлен финальный узел, который завершает запуск ошибкой, если хотя бы один день упал или отсутствует.
- Что ловит теперь: этот узел, проверенный на тестовой копии (7 из 7 дней → зелёный, 1 упавший день → красный), и метки свежести в утреннем отчёте. В репозитории тот же принцип проверяют `test_source_dates_produce_stale_fresh_and_no_data` и `stale orders show the missing target day…` в `tests/renderer.test.js`.

**Инцидент 2. Реклама в марже дня была занижена (08.10).**
- Что сломалось: в маржу по дням заказа попадала только реклама с оплатой за клик, а расход кампании «оплата за заказ» — нет. За сентябрь реклама в марже была занижена примерно на 40%, а расход «оплата за заказ» — примерно в 9 раз.
- Как заметили: расход на рекламу в марже дня не совпал с реестром расходов рекламного кабинета (в один из дней — в 2,3 раза).
- Что изменили: сначала проверили, что двойного учёта не будет (типы начислений сверены по дням), затем добавили в расход дня кампании, которых нет в статистике по товарам. Период 28.09–07.10 пересчитан из уже сохранённых сырых ответов новой ревизией; старая ревизия осталась (данные только дописываются). Маржа после рекламы за 05–07.10 стала ниже на 1,6–5 п.п. выручки.
- Что ловит теперь: если расход за день не загружен, ревизия помечается `PPO_EXPENSE_NOT_CAPTURED` вместо нуля; сверочное представление сравнивает расход с начислениями по типу. В репозитории — `test_missing_ads_cost_blocks_contribution_instead_of_zero_spend` и `unknown PPO spend and month ads do not become zero…`.

Найдено при подготовке портфолио (синтетика, не прод): в Docker и CI база работает в UTC, и отчёт показывал время на 3 часа раньше (05:48 вместо 08:48). Тесты этого не ловили, потому что локальная база была в московском поясе. Исправление в v0.3: экспорт фиксирует часовой пояс сессии, рендер переводит метки в Москву, добавлены тест экспорта в UTC-сессии и шаг CI, который сравнивает пересобранные `examples/` с закоммиченными.

## Ограничения

Репозиторий — синтетическая реконструкция, а не рабочая установка: SQL упрощён, n8n-экспорты обезличены и выключены, данные и параметры вымышлены. Тесты подтверждают поведение на контролируемых данных, но не полноту реальных источников, аптайм, бухгалтерскую корректность или эффект для бизнеса. Ответы в eval записаны через Grok Bot (не вызов API и не слепой замер). Цифры о реальной системе в разделах выше взяты из её журнала решений и отчётов агентов и даны в количествах и долях; эффекты — модельные оценки, а не измеренная экономия в рублях. Правила тестов и CI добавлены в v0.2–v0.3 и не выдаются за историю исходного проекта.
